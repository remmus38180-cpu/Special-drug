# 特殊藥品認定、調高及供貨合約管理系統

程式規格書 v0.4（單機HTML版）｜2026-10-18｜供業務確認、Claude開發

## 0. 本版修訂

v0.4改變執行形式，業務規則不變：

1. 程式由「免安裝桌面執行檔（exe）」改為「單一離線HTML檔」，以瀏覽器開啟。目的：exe易被機關防毒誤判、隔離。
2. 不支援多人同時編輯，改為「一人編輯、多人查詢」：開啟時選編輯或查詢，有人編輯中即不能進入編輯，並顯示目前編輯者（第4.6節）。取消v0.3.1之全系統獨占鎖、發布版本、查詢者副本及角色權限；T16、T23、T25至T32改以H17至H24驗收。
3. 資料改存使用者選定的本機資料夾（瀏覽器檔案系統存取），每次儲存保留完整版本，不覆寫。
4. 第3節業務規則B01至B19、第7至9節及第12節實質不變；第6節改以JSON集合實作同一資料模型。
5. 納入v0.3.1第二輪審查結論中與單機版相關者（第11.4節、第13節）。
6. v0.3.1 Python版程式保留於repo作邏輯參考，不再擴充。
7. 補充（2026-10-18）：所有匯出檔以匯出時間命名，並於檔名、檔案內容、檔案屬性、資料夾匯出紀錄四處標示版本（第11.5節）。
8. 補充（2026-10-18）：資料夾可放共用槽，以編輯登記檔協調單一編輯者（第4.6節），並於存檔前後檢查編輯權與版本。

## 1. 文件定位與依據

本版從基本收案開始，第一期即保存所有申請案件及歷次會議，包含通過、未通過、撤回與辦理中案件。公告複核時辦理認定、調高及註記登記。涵蓋主檔匯入、適用條件、價格歷程、供貨合約、查詢及驗收；補件提醒及排程等進階流程列為後續階段。

業務依據為本次討論及使用者提供「活頁簿1.xlsx」之final工作表（287筆資料、17欄）。原Excel內容是移轉來源，不能一律當作現行有效認定；其中含歷史名稱、取消案件、價格歸零、附帶條件及待釐清文字。

本文件引用第25條的適用關係，係依使用者說明建模，非重新查證法規。正式使用前由業務單位確認適用依據與起算時點。

規格標籤：
- 【已確認】：使用者已明確說明或同意的業務規則。
- 【設計建議】：本版供開發採用的技術或操作設計，可再修訂。
- 【待確認】：不得由程式推定、不得硬編為正式業務規則。

## 2. 目標與範圍

### 2.1 要解決的問題

1. Excel多版本並存，不易確認最新檔案及所在位置。
2. 主檔只有是否註記，無法追溯認定範圍、依據、歷程及附帶條件。
3. 合約個別保存，難查詢、交接及核對調高前提。
4. 核價與調價單位都可能辦理相關品項，須能匯出共用認定與品項資料。
5. 手打分組、ATC及藥品代碼易誤植；需以匯入主檔點選及預覽取代。
6. 後續價差監測需查詢指定日期的認定與品項註記，不能只看目前狀態。

### 2.2 第一期必做（P0）

- 單一離線HTML檔，函式庫內嵌，不連外網，不需安裝。
- 基本收案、案件清單及逐品項處理結果，不以是否通過作收錄限制。
- 歷次專家會議、藥事小組及共同擬訂會議登記，保存建議、決議及文件。
- 既有Excel匯入預覽及待核對歷史資料，不直接全部認定現行有效。
- 認定項目、認定版本、適用條件及依據文件管理。
- 主檔Excel／CSV匯入、欄位映射、版本保存及差異比較。
- 條件點選、符合名單預覽、確認名單快照。
- 公告複核登記、個別品項調高與註記、合約基本資料及附件。
- 草稿、待確認、已確認及撤銷管理；歷史查詢、稽核紀錄。
- 查詢、匯出、備份與還原；儲存版本保留與完整性檢查。

### 2.3 後續階段（P1）

- 補件通知與提醒、提會排程、期限及進階案件流程。
- 供貨履約紀錄、合約到期及附帶條件提醒。
- 公文系統及正式藥品主檔介接。
- 跨品項複合條件的自動判定；P0先提供人工確認。
- 多人共用（如有需要，另案評估受控服務；不以共用資料夾多人同時開啟替代）。

### 2.4 不在本期範圍

不自動決定調高價格、不直接修改機關正式藥品主檔、不計算DET、不做藥價調查申報真偽查核、不將資料傳送外部服務或AI。系統內登記確認不取代公文核定。不支援多人同時編輯（一人編輯、多人查詢見第4.6節）。

## 3. 核心業務規則

（與v0.3.1相同，不得變更）

| ID | 狀態 | 規則 |
|---|---|---|
| B01 | 已確認 | 管理有核價、調價兩個單位，相關認定資料須共同查詢。 |
| B02 | 已確認 | 調價依分類分組；依使用者說明，有品項建議提高通過後，相關分組不再依DET調整，改依第25條處理。適用起日另待確認。 |
| B03 | 已確認 | 只有實際調高的個別品項才註記，不能把所有符合認定範圍品項一律註記。 |
| B04 | 已確認 | 目前每項均須完成穩定供貨簽約才能調高；歷史上僅不可替代類別要求簽約。不得倒套現行要求。 |
| B05 | 已確認 | 符合既有認定範圍的新收載品項，可接續簽約及價格辦理。認定與各品項實際辦理結果分開存。 |
| B06 | 已確認 | 認定範圍不僅分組，尚有ATC、劑型、單複方、規格、指定品項、排除及跨品項條件。 |
| B07 | 已確認 | 由使用者在同仁陳核公告、進行複核時登記；以主檔點選減少誤植。 |
| B08 | 已確認 | 調高生效日與註記生效日分欄保存；歷史無須簽約、未簽、已簽及待確認須區分。 |
| B09 | 設計建議 | 認定類別、調價路徑、合約、調高、主檔註記是不同概念，不以單一狀態欄替代。 |
| B10 | 設計建議 | 認定取消、類別變更、資料更正均新增版本；不覆寫已確認歷程。 |
| B11 | 設計建議 | 合約到期、新主檔匯入、價格日後調整，不自動取消認定或註記。 |

- B12【已確認】：未通過案件也須保存提案的專家會議及共同擬訂會議紀錄。
- B13【設計建議】：案件與認定分開；沒有通過認定的案件仍可獨立存在並完整查詢。
- B14【設計建議】：同案可多次提會，同次會議可處理多案；每個議案可有不同品項結果。專家建議與共同擬訂會議決議分開標示，不相互覆蓋。
- B15【設計建議】：新申請未通過不新增有效認定／註記，也不得自動取消該藥先前已有效的認定；取消須另有依據。
- B16【已確認】：歷史類別名稱為改名，非不同類別：「不可替代必要藥品」即現行「不可替代特殊藥品」，「必要藥品」即現行「特殊藥品」。移轉時自動對照為現行名稱，原名稱保存於原始類別欄；系統類別選項只列現行名稱。
- B17【已確認】：簽約要求選「待確認」者，系統不以案件來源限制其確認；由確認者依個案判斷，系統仍保存「不完整」標示。
- B18【已確認】：調高確認時，系統不檢查對應合約之生效日及到期日是否涵蓋調高生效日；仍檢查合約已完成簽署及適用品項。
- B19【已確認】：會議決議逐品項結果為「附條件同意」者，系統不另設條件達成欄位或檢核；條件內容保存於結果原文及條件欄。

重要界線：以條件篩出的「認定範圍名單」，不等於「本次調高名單」，也不等於「主檔實際註記名單」。三者須能個別查詢及核對。

## 4. 執行環境與檔案形式

### 4.1 已知決定

- 【已確認】交付單一 `.html` 檔，以機關電腦瀏覽器直接開啟（`file://`），不需安裝、不需系統管理權限、不需網路。
- 【已確認】同一時間只允許一人編輯；其他人可同時以查詢模式開啟（第4.6節）。
- 【已確認】使用環境：每人使用自己的桌機，以員編及密碼登入Windows，再由檔案總管已設定之網路位置（共用槽）開啟程式。
- 【設計建議】HTML程式檔與資料夾都放共用槽，例：`\\伺服器\共用\特藥系統\特殊藥品管理_v0.4.0.html` 與 `\\伺服器\共用\特藥系統\資料\`。HTML開啟後即載入各人瀏覽器執行，不佔用檔案，更新程式直接替換HTML，已開啟者重新整理即換新版。
- 【待確認】雙擊HTML時使用各電腦預設瀏覽器，須統一為支援檔案系統存取之瀏覽器（Q08）；瀏覽器重開後可能須再點一次「允許」存取資料夾。
- 【設計建議】資料存放於使用者選定的資料夾（本機、個人網路磁碟或共用槽），由瀏覽器「檔案系統存取」功能讀寫。HTML程式檔與資料分開；更新程式只換HTML，不動資料。

### 4.2 防毒誤判之避免【設計建議】

1. 只交付 `.html` 及說明文件；不交付或要求執行 exe、bat、cmd、vbs、ps1、hta、jar、含巨集Office檔。
2. 所有函式庫（Excel讀寫、zip、日期、十進位）內嵌於HTML，保留原授權標頭與版本號；不從CDN或任何網址載入；不載入外部字型。
3. 程式碼不使用 `eval`、`new Function`、字串形式 `setTimeout／setInterval`、`document.write`；不混淆；不內嵌base64可執行碼；P0不使用WebAssembly。
4. 開啟時不自動下載、不自動開新視窗、不嵌入隱藏iframe；下載一律由使用者按鈕觸發。
5. 防毒是否誤判以實機驗收為準（H01）；程式不宣稱保證不被誤判。

### 4.3 瀏覽器能力與啟動自檢

啟動即顯示自檢結果並保存於畫面「關於」：

| 檢查 | 用途 | 未通過時 |
|---|---|---|
| 安全環境（`isSecureContext`） | 雜湊、UUID、檔案存取 | 停用編輯 |
| `crypto.subtle`、`crypto.randomUUID` | SHA-256、主鍵 | 停用編輯 |
| `showDirectoryPicker`（檔案系統存取） | 資料夾讀寫 | 唯讀模式：僅能開啟備份zip查詢及匯出 |
| `indexedDB` | 記住資料夾授權、當機復原草稿 | 可編輯，但提示無當機復原 |
| `navigator.locks` | 防止同瀏覽器兩分頁同時編輯 | 可編輯，但提示勿開兩分頁 |
| 資料夾寫入測試（建立並刪除暫存測試檔） | 判斷是否具寫入權 | 只提供查詢模式並說明原因 |

【待確認】機關瀏覽器種類、版本，`file://` 開啟時上述能力是否可用，及群組原則是否停用檔案系統存取（Q08）。未實測前不宣稱可用。

### 4.4 資料夾結構

使用者首次使用時選定空資料夾作「資料夾」，程式建立：

```
<資料夾>/
  specdrug.json              資料夾識別：folder_id、建立時間、資料結構版本
  control/editing.json       編輯登記：目前編輯者、工作階段、心跳（第4.6節）；不刪檔，結束時改寫為已結束
  data/current.json          目前版本指標：版本檔名、SHA-256、revision、save_id、儲存時間
  data/versions/             每次儲存的完整業務資料，一次寫入、不覆寫
    r000123-20261018T024501Z-<sha前8碼>.json
  masters/<import_id>.json   主檔匯入列資料，一次寫入、不覆寫
  attachments/<sha前2碼>/<sha256>   附件（含主檔與移轉來源檔），以雜湊為檔名
  backups/                   使用者匯出的備份zip（可另存他處）
  logs/export-log.jsonl      匯出紀錄（每次匯出追加一列；第11.5節）
```

不以使用者輸入的檔名組成路徑；所有檔名由程式依上列格式產生並驗證。

### 4.5 儲存與開啟協定【設計建議】

工作狀態分兩層，畫面明示：
- 「未儲存變更」：記憶體中，並即時寫入瀏覽器IndexedDB作當機復原草稿。
- 「已儲存」：寫入資料夾形成新版本。

業務狀態「草稿／待確認／已確認／撤銷」與上述儲存狀態是不同概念，不得混用。

儲存（單一程序，任何步驟失敗即整體失敗，不改目前版本）：

1. 讀 `control/editing.json`，確認工作階段id仍為本工作階段；不是（已被接手）即拒絕儲存，未儲存變更保留為復原草稿。再讀 `current.json`，確認 revision 與本次開啟時相同；不同即拒絕儲存，保留未儲存變更，提示「資料夾已被其他分頁或程式變更，請重新載入核對」，不整份覆蓋。
2. 驗證本次變更：引用之附件、主檔檔案存在且雜湊相符；稽核雜湊鏈連續。
3. 序列化業務資料（含 `save_id`），算SHA-256，寫入新版本檔；寫完讀回比對雜湊。
4. 寫入新 `current.json`（revision＋1）。
5. 重讀 `current.json`，其 `save_id` 須為本次；不是即警告「目前版本已被其他人覆蓋」，列出本次版本檔名以供找回，不清除復原草稿。
6. 成功後才更新畫面「已儲存」狀態並清除對應復原草稿。

重試：步驟4後若畫面未得到結果（斷線、當機），再按儲存或重開時，先讀 `current.json`：若其 `save_id` 等於本次待儲存之 `save_id`，視為已完成，不再建立版本。

開啟：讀 `current.json`→讀版本檔→驗SHA-256與資料結構版本→驗稽核雜湊鏈。任一不符即顯示原因並列出 `data/versions/` 供使用者選擇，不自動改用其他版本、不靜默修正。資料結構版本新於本程式時只可唯讀。

當機復原：重開時若IndexedDB有復原草稿，且其基準revision等於目前revision，詢問復原或放棄；基準不同時另存為復原檔供核對，不自動套用。

同瀏覽器兩分頁：以 `navigator.locks`（鎖名含folder_id）只准一個分頁編輯，其他分頁唯讀並顯示原因。

### 4.6 編輯與查詢模式【已確認：使用者要求；細節為設計建議】

1. 開啟資料夾後選「查詢」或「編輯」。查詢模式唯讀，可查詢、匯出、下載附件，不產生未儲存變更。
2. 使用者名稱：瀏覽器基於安全限制，網頁無法讀取Windows登入帳號（員編）及電腦名稱。首次使用時輸入「員編／姓名」及「電腦代號」，存於該Windows帳號的瀏覽器設定中，之後自動帶入；換人登入同一台電腦時，因瀏覽器設定隨Windows帳號分開，須重新輸入。此名稱供顯示與稽核記錄，非身分驗證。以捷徑網址參數帶入登入帳號之可行性待實測（Q14）。
3. 編輯登記檔 `control/editing.json` 內容：狀態（編輯中／已結束）、使用者名稱、電腦代號、工作階段id、開始時間、心跳序號、最後心跳時間、程式版本、基準revision、接手紀錄。
4. 選「編輯」時：
   - 讀登記檔。他人「編輯中」且仍有回應→不可進入編輯，跳提示：「目前由 ○○○（電腦：○○）自 10:12 起編輯中，最後回應 10:45。請待對方結束編輯，或以查詢模式開啟。」按鈕：以查詢模式開啟、重新檢查。
   - 無人編輯→寫入自己的登記，等3秒後重讀；仍為自己才進入編輯，否則退回並顯示對方資訊（同時搶按時之處理）。
5. 是否仍有回應：以登記檔之檔案修改時間（由檔案系統提供）與本機時間比較，5分鐘內有更新視為仍有回應。檔案時間與本機時間差異異常（如在未來2分鐘以上）時，改以本機連續觀察心跳序號是否變動判定，判定期間顯示「確認中」。
   情境例（A先編輯，B後到）：

   | 時間 | 發生的事 | 登記檔 | B按「編輯」的結果 |
   |---|---|---|---|
   | 10:00 | A選編輯 | 寫入：A、編輯中、10:00 | — |
   | 10:00起 | A的程式每30秒更新登記檔 | 檔案修改時間跟著更新 | — |
   | 10:20 | B選編輯 | 最後更新10:19:40 | 擋下，提示「目前由A自10:00起編輯中，最後回應10:19」 |
   | 10:30 | A沒按結束直接關瀏覽器 | 停在10:30，不再更新 | — |
   | 10:33 | B再試 | 3分鐘前 | 仍擋下（未滿5分鐘，可能只是背景或網路慢） |
   | 10:36 | B再試 | 6分鐘前 | 顯示「A疑似離線」；B聯繫A後填原因，可確認接手 |
   | （另例）10:30 | A按「結束編輯」 | 改寫為已結束 | B立即可進入編輯 |

   兩人同時按：A、B都看到無人編輯，都寫入自己名字；檔案只會留下後寫者的名字。兩人各等3秒再讀，名字仍是自己者進入編輯，另一人退回並看到對方資訊。
6. 疑似離線（超過5分鐘無回應，如當機、關機、休眠、斷線、未按結束即關閉）：不自動接手、不刪檔。顯示登記者及最後回應時間，提示「對方可能當機、關機或斷線，強制接手前請先聯繫對方」；須填接手原因並確認，接手紀錄寫入登記檔，並於下次存檔寫入稽核。
7. 編輯中每30秒更新心跳；狀態列顯示「編輯中」。分頁在背景時瀏覽器可能降低更新頻率，5分鐘判定已容許。心跳寫入失敗（斷線、權限）時立即停止存檔，提示「編輯權狀態不明」；恢復後須重讀登記，確認仍為自己且未被接手，才可再存檔。
8. 舊編輯者恢復：若已被他人接手，存檔被拒（第4.5節步驟1），未儲存變更保留為復原草稿供核對重套，不整份覆蓋。
9. 結束編輯：按「結束編輯」→有未儲存變更先選儲存、保留本機草稿或放棄→登記檔改寫為「已結束」。關閉分頁時嘗試改寫，但瀏覽器不保證完成；未完成者依第5點逾時判定。
10. 查詢模式狀態列顯示「目前編輯者：○○○（自 10:12）」或「目前無人編輯」；每分鐘檢查 `current.json`，有新版提示重新載入，不在查詢中途混用版本。
11. 心跳間隔30秒、離線判定5分鐘為預設，可於設定調整（Q13）。
12. 限制（須接受）：此為協調機制，不是檔案伺服器仲裁的獨占鎖，瀏覽器無此能力。兩人於數秒內同時按編輯，或網路磁碟快取延遲時，仍可能兩人都進入編輯；此時以第4.5節之編輯權、revision檢查及存檔後重讀，使後存者被拒或立即警告，已存版本不被靜默取代，但可能需人工重套。
13. 建議搭配共用槽權限：只給需編輯者寫入權；其他人唯讀，程式偵測不可寫入時只提供查詢模式。共用槽權限依員編登入之Windows帳號由檔案伺服器執行，是本系統唯一由伺服器把關的控管。
14. 伺服器端佐證：檔案伺服器通常記錄每個檔案的擁有者（建立該檔之Windows帳號）。每次儲存新建版本檔、編輯登記檔改寫時，其擁有者即為實際操作之員編帳號，管理者可於檔案總管「內容→安全性→進階」核對，與程式內自行輸入之名稱互相印證。程式本身讀不到此資訊；是否如此記錄依伺服器設定，待實測（Q15）。

### 4.7 介面與程式分層

介面、業務邏輯、資料存取（資料夾／IndexedDB）分開模組；業務邏輯為純函式模組，可在Node測試環境執行。開發時可分檔撰寫，以建置腳本合併為單一HTML；使用者端不需建置工具。

## 5. 使用者與操作紀錄

- 【設計建議】不設角色權限；以編輯／查詢模式區分（第4.6節）。稽核以本機設定之使用者名稱及電腦代號記錄；此名稱非身分驗證。

## 6. 資料結構

### 6.1 共通約定

- 主鍵採UUID（`crypto.randomUUID`）；業務顯示編號另建，不用分組代碼作永久主鍵。
- 藥品／分組／ATC／廠商代碼皆文字型別，保留前導零；Excel讀入時以原儲存格文字為準，不經數值轉換。
- 金額以十進位字串保存，運算使用內嵌十進位函式庫或整數換算；禁止以JavaScript浮點數直接計算或保存價格。
- 日期採 `YYYY-MM-DD` 字串，介面可顯示民國年；時間採UTC ISO字串保存、Asia/Taipei顯示。
- 有效期間採起日含、迄日不含；空白迄日代表無已知終止日，不代表永久有效。
- 歷史未知日期可為空，但須標記待確認；不得用會議日補成生效日。
- 已確認資料不原地修改；更正建立新版本或取代紀錄，保留原內容、修改人、時間與原因。
- 記錄建立者、建立時間、更新者、更新時間、row_version；正式資料以撤銷／取代保留，不硬刪。

## 7. 主檔匯入

1. 支援.xlsx及UTF-8 CSV（含BOM與否皆可）；使用者選工作表、標題列及欄位映射，不依固定欄序。
2. 匯入必要欄位為藥品代碼。各類規則用到的欄位須存在，缺少時停用該類規則並明示原因，不以空白當不符合。
3. 同一快照一個代碼一列。完全相同重複列可在確認後合併；內容矛盾列阻止啟用。若來源為多期價格長表，先要求指定基準日期及期間映射，不任取第一筆。
4. 代碼去除前後空白；保留原值與正規化值；不自動把O改0。數值型儲存格代碼可能遺失前導零時列為錯誤，不自行補碼。
5. 規格分成數值及單位；只做經確認的單位映射，未知單位待確認。
6. 試匯入顯示總筆數、重複、缺漏、未知值及差異；確認後啟用。啟用前列資料先寫入 `masters/` 並驗雜湊，失敗不改目前主檔版本。
7. 新快照保留舊版。比較新增／消失品項、分組、ATC、劑型、規格、廠商、價格及註記異動。
8. 主檔消失品項不自動刪除認定或解讀成取消給付。
9. 來源檔以附件保存（雜湊、基準日）。畫面明示目前引用哪一版主檔。
10. 效能：5萬列匯入須顯示進度，不凍結畫面（可用Web Worker；Worker程式碼亦內嵌於同一HTML，以Blob建立）。

## 8. 條件選取與判定引擎

### 8.1 UI支援

分組多選、ATC完整碼多選、ATC前綴、核價劑型多選、單複方、規格數值與單位、藥品代碼納入／排除。選項由主檔產生；同時顯示代碼與中文說明。組合支援全部符合（AND）、任一符合（OR）、排除（NOT），以可展開條件群組表示。

常用範本：依分組、依ATC加劑型、依分組加規格、指定品項、進階條件。首次不要求使用者看到JSON。

### 8.2 儲存格式

儲存結構化AST，禁止把Excel文字當程式執行；禁止 `eval`、`new Function`。欄位、運算子及型別皆採白名單。

```json
{
  "op": "or",
  "children": [
    {"op": "and", "children": [
      {"field": "atc_code", "op": "starts_with", "value": "J06B"},
      {"field": "atc_code", "op": "not_in", "values": ["J06BB16"]}
    ]},
    {"field": "atc_code", "op": "in", "values": ["L04AA03", "L04AA04"]}
  ]
}
```

判定結果採符合／不符合／待確認三值。欄位缺失、未知單位或人工條件未完成時為待確認；NOT待確認仍為待確認。AND有不符合即不符合，否則有待確認則待確認；OR有符合即符合，否則有待確認則待確認。前綴比對以文字起始位置。空規則禁止當作全選。

### 8.3 特殊情形

與v0.3.1第8.3節相同（Warfarin同廠牌、「=0」、RO5DA04、部分涵蓋分組、多項認定衝突）。

### 9.2 公告複核登記

1. 開啟或建立公告案件，登錄公文、承辦及來源資料。
2. 搜尋既有認定項目；新增或建立變更版本，避免重複認定。
3. 登錄會議決議及範圍原文，選取已啟用之主檔版本。
4. 點選條件，執行預覽；列出符合分組、符合藥品及待確認項目。
5. 核對認定範圍；涉及部分分組、排除或跨品項條件時明列提示。
6. 從範圍名單勾選本次調高品項，逐項登錄價格、簽約要求、合約及預定註記；範圍外品項不可直接勾入，須另補認定依據。
7. 儲存為草稿／待確認。陳核階段不更新正式現況。
8. 核定後補正式文號、日期及各生效日期，經確認對話框確認。
9. 確認時版本、快照、品項事件及稽核紀錄在記憶體中整批成立，並依第4.5節儲存為新版本；驗證失敗整批不成立。
10. 到生效日後，查詢結果依有效期間呈現。
11. 匯入正式主檔後比對註記及價格，產生待核對清單；本系統不直接更新正式主檔。

現行案件須簽約卻缺完成簽署合約，不得確認調高結果；合約之生效日及到期日不列入此檢查（B18）。歷史案選「當時無須簽約」須有說明／依據。簽約要求「待確認」不以案件來源限制（B17），確認時標示不完整。

3. 已確認之認定版本，其範圍名單擴增（新快照確認）須經確認對話框，列出新增品項，並記錄稽核；快照只能採「已啟用」主檔。
4. 已確認資料（認定版本、已確認快照名單、已確認調高與註記、已確認分組調價方式）無修改入口；更正以新版本或取代紀錄辦理。
5. 稽核紀錄只追加；每筆含前一筆雜湊（雜湊鏈），開啟時驗證，斷鏈即警示並列出位置，不自動修補。
6. 業務邏輯模組不讀寫DOM；介面只能呼叫業務模組函式改資料，不直接改資料物件。

### 11.5 匯出檔命名與版本標示【設計建議】

資料儲存在資料夾即完成，不需匯出；匯出是另產給人看或交給他人的檔案。匯出種類：查詢結果、認定清單、品項明細、差異待辦、移轉核對清單（CSV／xlsx）、備份（zip）、列印畫面。

**一、檔名**

格式：`特藥_<內容>_<匯出時間>_r<revision>.<副檔名>`

- 匯出時間：Asia/Taipei，西元 `YYYYMMDD-HHMMSS`，例 `20261018-124805`；精確到秒；同一秒內再次匯出同類檔案時，於時間後加 `-2`、`-3`。
- revision：匯出當下所依據之已儲存版本號，6位補零，例 `r000123`；有未儲存變更時改為 `r000123+未儲存`，並於匯出前提示。
- 內容：程式固定名稱（認定清單、品項明細、差異待辦、查詢結果、移轉核對、備份），不含使用者輸入文字，不含 `\ / : * ? " < > |`。
- 例：`特藥_認定清單_20261018-124805_r000123.xlsx`、`特藥_備份_20261018-124805_r000123.zip`。
- 匯出時以「另存」對話框帶入預設檔名，使用者可改名；檔名被改不影響下列內嵌版本資訊。

**二、檔案內容**

| 檔案 | 寫入位置 | 內容 |
|---|---|---|
| xlsx | 第一個工作表「匯出說明」 | 匯出時間（台北時間及UTC）、操作者、程式版本、資料結構版本、資料revision、版本檔SHA-256前16碼、主檔版本與資料基準日、查詢條件、查詢日期、筆數；資料工作表在其後 |
| CSV | 檔首說明列（以 `#` 開頭，同上欄位） | 設定可改為不加說明列（供SAS等程式直接讀入），此時另產同名 `_說明.txt` |
| zip備份 | `backup_manifest.json` 及zip註解欄 | 第13節manifest欄位，另加匯出時間、程式版本 |
| 列印畫面 | 每頁頁尾（列印樣式） | 程式版本、資料revision、列印時間、頁次 |

**三、檔案屬性**

xlsx寫入文件摘要屬性：標題（內容名稱）、作者（操作者）、建立時間（匯出時間）、主旨（查詢條件摘要），並以自訂屬性寫入程式版本、資料結構版本、資料revision、主檔基準日。函式庫不支援之屬性於驗收文件註明，不影響「匯出說明」工作表。

**四、資料夾匯出紀錄**

每次匯出成功後於 `logs/export-log.jsonl` 追加一列：匯出時間、檔名、種類、查詢條件、筆數、資料revision、程式版本、匯出檔SHA-256。匯出紀錄不改變業務資料、不產生未儲存變更。畫面「儲存歷程」可查匯出紀錄；可依檔案SHA-256反查某份匯出檔來自哪個版本。寫入失敗時提示，但不影響已下載檔案。

**五、其他版本標示處**

- 程式本身：檔名 `特殊藥品管理_v<程式版本>.html`；`<title>`、`<meta name="version">`、狀態列及「關於」畫面顯示程式版本、資料結構版本、建置日期與原始碼commit前7碼。
- 每個資料版本檔：檔頭欄位程式版本、資料結構版本、revision、上一版revision及SHA-256、儲存時間、操作者、save_id。
- `current.json`：同上摘要，供不開啟程式時辨識。
- 稽核紀錄：每筆記錄當時程式版本。

## 13. 資料安全、備份與還原

- 資料僅存於使用者選定資料夾及本機瀏覽器IndexedDB（復原草稿）；不上傳、不連外。
- 附件以SHA-256為儲存鍵，不以使用者檔名當路徑；另存附件時檔名去除路徑與不合法字元；讀取一律驗雜湊。上傳型別及大小可設定，P0預設上限50MB。
- 資料夾內容可被瀏覽器以外的程式修改；本系統以雜湊、雜湊鏈及revision偵測，非防竄改安全邊界。
- 匯出備份：產生zip，內含目前版本檔、`current.json` 內容、所有被引用之 `masters/` 與附件，及 `backup_manifest.json`（每個檔案路徑、大小、SHA-256、來源revision、建立時間、程式版本）。檔名依第11.5節。產生後重新讀取zip逐檔驗證。
- 驗證備份：manifest須列出資料版本檔且恰為一份；每個路徑須符合第4.4節格式，不得含 `..`、絕對路徑或磁碟代號；資料內每筆附件及主檔均須在manifest列出且雜湊相符；manifest外的檔案視為錯誤。
- 還原：須填原因；只寫入新版本（revision＋1），既有版本檔不改不刪；附件與主檔檔案已存在且雜湊相符則沿用，不符即中止；稽核記錄「還原」及來源備份資訊。另提供「還原至新資料夾」供演練。
- 大量匯入前提示先匯出備份。程式不在背景自動備份；保存期限與異地存放由單位確認（Q09）。
- CSV／Excel匯出防公式注入；檔名、匯出說明、屬性及匯出紀錄依第11.5節。

## 16. 開發順序與交付清單

順序：自檢與資料夾存取（含儲存協定、雜湊、復原草稿、編輯登記）→ 資料模型與模擬資料 → 基本收案及歷次會議 → 主檔匯入 → 規則編輯／預覽 → 認定版本／快照 → 公告品項／合約 → 查詢／差異／匯出 → 備份還原 → Excel移轉預覽。

交付：
- 單一HTML檔（例：`特殊藥品管理_v0.4.0.html`），檔內標示程式版本、資料結構版本、建置日期及commit（第11.5節）。
- 原始碼、建置腳本、鎖定版本之內嵌函式庫（含授權檔）、資料結構升級程式。
- 自動化測試（業務邏輯以Node執行；資料夾存取可用瀏覽器私有檔案系統或模擬介面）及結果。
- 模擬資料（可由HTML內「載入示範資料到新資料夾」產生，不得載入到既有正式資料夾）。
- 使用說明（含資料夾選擇、儲存、備份還原、換電腦搬移資料夾、程式更新）、驗收結果、已知限制及待確認事項。

不得只交靜態畫面、或只存在瀏覽器localStorage／IndexedDB而宣稱完成。首次開啟不得載入真實合約或將附檔自動轉成正式有效資料。正式資料不得寫進HTML原始碼。
