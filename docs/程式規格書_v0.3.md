# 特殊藥品認定、調高及供貨合約管理系統

程式規格書 v0.3｜2026-10-17｜供業務確認、Claude開發及資訊需求評估

本次修訂：第一期納入基本收案、通過與未通過案件、歷次專家及共同擬訂會議、逐品項決議及歷史案件匯入；沿用v0.2共用槽單人編輯多人查詢架構。

## 1. 文件定位與依據

本版從基本收案開始，第一期即保存所有申請案件及歷次會議，包含通過、未通過、撤回與辦理中案件。公告複核時辦理認定、調高及註記登記。涵蓋主檔匯入、適用條件、價格歷程、供貨合約、共同查詢及驗收；補件提醒及排程等進階流程列為後續階段。

業務依據為本次討論及使用者提供「活頁簿1.xlsx」之final工作表（287筆資料、17欄）。原Excel內容是移轉來源，不能一律當作現行有效認定；其中含歷史名稱、取消案件、價格歸零、附帶條件及待釐清文字。

本文件引用第25條的適用關係，係依使用者說明建模，非重新查證法規。正式上線前由業務單位確認適用依據與起算時點。

規格標籤：
- 【已確認】：使用者已明確說明或同意的業務規則。
- 【設計建議】：本版供開發採用的技術或操作設計，可再修訂。
- 【待確認】：不得由程式推定、不得硬編為正式業務規則。

## 2. 目標與範圍

### 2.1 要解決的問題

1. Excel多版本並存，相關同仁未必知道最新檔案及所在位置。
2. 主檔只有是否註記，無法追溯認定範圍、依據、歷程及附帶條件。
3. 合約由承辦個別保存，難共同查詢、交接及核對調高前提。
4. 核價與調價單位都可能辦理相關品項，須共用認定與品項資料。
5. 手打分組、ATC及藥品代碼易誤植；需以匯入主檔點選及預覽取代。
6. 後續價差監測需查詢指定日期的認定與品項註記，不能只看目前狀態。

### 2.2 第一期必做（P0）

- 基本收案、案件清單及逐品項處理結果，不以是否通過作收錄限制。
- 歷次專家會議、藥事小組及共同擬訂會議登記，保存建議、決議及文件。
- 由開發者製作既有Excel匯入工具及待核對歷史資料，不直接全部認定現行有效。

- 認定項目、認定版本、適用條件及依據文件管理。
- 主檔Excel／CSV匯入、欄位映射、版本保存及差異比較。
- 條件點選、符合名單預覽、確認名單快照。
- 公告複核登記、個別品項調高與註記、合約基本資料及附件。
- 草稿、待確認、已確認及撤銷管理；歷史查詢、稽核紀錄。
- 查詢、匯出、資料備份；多人版須有身分辨識及更新衝突處理。

### 2.3 後續階段（P1）

- 補件通知與提醒、提會排程、期限及進階案件流程；基本收案與會議紀錄已列P0。
- 供貨履約紀錄、合約到期及附帶條件提醒。
- 公文系統及正式藥品主檔介接。
- 跨品項複合條件的自動判定；P0先提供人工確認。

### 2.4 不在本期範圍

不自動決定調高價格、不直接修改機關正式藥品主檔、不計算DET、不做藥價調查申報真偽查核、不將資料傳送外部AI服務。系統內登記確認不取代公文核定。

## 3. 核心業務規則

| ID | 狀態 | 規則 |
|---|---|---|
| B01 | 已確認 | 管理有核價、調價兩個單位，相關認定資料須共同查詢。 |
| B02 | 已確認 | 調價依分類分組；依使用者說明，有品項建議提高通過後，相關分組不再依DET調整，改依第25條處理。適用起日另待確認。 |
| B03 | 已確認 | 只有實際調高的個別品項才註記，不能把所有符合認定範圍品項一律註記。 |
| B04 | 已確認 | 目前每項均須完成穩定供貨簽約才能調高；歷史上僅不可替代類別要求簽約。不得倒套現行要求。 |
| B05 | 已確認 | 符合既有認定範圍的新收載品項，可接續簽約及價格辦理。認定與各品項實際辦理結果分開存。 |
| B06 | 已確認 | 認定範圍不僅分組，尚有ATC、劑型、單複方、規格、指定品項、排除及跨品項條件。 |
| B07 | 已確認 | 由使用者在同仁陳核公告、進行複核時登記；以主檔點選減少誤植。 |
| B08 | 已確認 | 調高生效日與註記生效日分欄保存；歷史無須簽約、未簽、已簽及待確認須區分。 |
| B09 | 設計建議 | 認定類別、調價路徑、合約、調高、主檔註記是不同概念，不以單一狀態欄替代。 |
| B10 | 設計建議 | 認定取消、類別變更、資料更正均新增版本；不覆寫已確認歷程。 |
| B11 | 設計建議 | 合約到期、新主檔匯入、價格日後調整，不自動取消認定或註記。 |

新增業務規則：
- B12【已確認】：未通過案件也須保存提案的專家會議及共同擬訂會議紀錄。
- B13【設計建議】：案件與認定分開；沒有通過認定的案件仍可獨立存在並完整查詢。
- B14【設計建議】：同案可多次提會，同次會議可處理多案；每個議案可有不同品項結果。專家建議與共同擬訂會議決議分開標示，不相互覆蓋。
- B15【設計建議】：新申請未通過不新增有效認定／註記，也不得自動取消該藥先前已有效的認定；取消須另有依據。

重要界線：以條件篩出的「認定範圍名單」，不等於「本次調高名單」，也不等於「主檔實際註記名單」。三者須能個別查詢及核對。

## 4. 部署與使用模式

### 4.1 已知環境與決定

使用科內網路共用磁碟機。採免安裝桌面程式，單人編輯、多人查詢；不另設持續運作的應用伺服器或資料庫服務。不要求GitHub、雲端部署或網路API。開發環境與執行環境分開；使用者電腦不需另裝Python、Node.js或資料庫軟體。

### 4.2 正式架構

所有人開啟程式預設為查詢模式，讀取共用槽已發布資料。點選「開始編輯」並取得全系統獨占編輯權後，才可修改。其他人持續查詢上一個完整版本，並看到編輯者與開始時間。

程式採「編輯鎖定、工作副本、完整版本發布」：

- 編輯者將最新已發布資料複製至本機工作區修改；查詢者也使用經驗證的本機唯讀副本。
- 共用槽保存不可覆寫的發布版本、附件、目前版本指標及鎖定資訊；不讓多台電腦直接開啟共用槽SQLite資料庫。
- 每次發布先驗證資料與附件完整，再切換目前版本；失敗保留舊版。
- 顯示查詢版本、發布時間及是否離線；有新版時提示更新，不在查詢中途混用不同版本。
- 儲存草稿與發布資料分開：草稿存本機可復原工作區；發布才能供他人取得。已發布資料可含具草稿狀態的案件，但不得當成正式認定，顯示權限依角色處理。
- 結束編輯前提示發布、保留本機草稿或放棄；未發布草稿不能宣稱已共同保存。

【設計建議】桌面介面、業務邏輯與本機資料存取分層；SQLite可作本機資料庫，整合為免安裝執行套件。程式包應含必要執行元件。具體語言及GUI框架由開發者評估機關作業系統後選定，不預設網頁前後端框架。

程式可放共用槽發行，直接執行或複製受控版本到本機執行，依機關政策及實測決定。程式更新不得覆寫正在使用的版本；記錄程式版本與資料結構版本，舊程式遇不支援資料格式時阻止編輯。

### 4.3 共用槽發布與鎖定契約

共用目錄分為app（程式版本）、control（編輯鎖與目前版本指標）、releases（不可變資料版本）、attachments（不可變附件）、staging（未完成發布）及backups（備份）。各發布版本具manifest，列出版本id、父版本、操作者、時間、資料結構版本及檔案雜湊。

編輯權必須使用共用檔案系統實際支援、由檔案伺服端仲裁的獨占檔案鎖／獨占開啟控制；不得只檢查某個lock檔是否存在。維持同一鎖定控制物件，不以刪除重建鎖檔強制交接。顯示用編輯者資料不是鎖本身。

發布期間必須持續持有有效獨占權，並確認目前版本仍是開始編輯的基準版本。將完整資料寫入唯一staging目錄、關閉資料庫並驗證完整性及附件雜湊後，形成不可變release；最後以實測支援的同檔案系統不可分割替換切換版本指標。版本檢查與切換皆在同一獨占權下完成，不能先釋放鎖再發布。

斷線或鎖有效性不明時，立即禁止發布；本機內容僅可保留為待復原草稿。重新連線須重新取得編輯權並重新比對基準版本；若已變更，不得整份覆蓋，應由使用者核對後重套變更。不得因心跳逾時就自動刪鎖或允許兩個編輯者。管理者解除異常鎖前，須透過共用槽管理機制確認舊連線／控制代碼已失效；無法確認就維持只讀。

鎖定與不可分割替換是正式上線的環境驗收條件。須在實際共用槽測試斷線、重新連線、快取、檔案占用及舊編輯者復活；不支援時不得以簡易檔案旗標替代或宣稱多人共用版完成。

## 5. 使用者與權限

| 角色 | 權限 |
|---|---|
| 查詢者 | 查詢已確認資料、依授權下載附件及匯出 |
| 登記者 | 建立案件與認定草稿、選條件、登錄合約與價格、預覽差異 |
| 複核登記者 | 確認登記內容、建立正式版本、登錄取消及更正；目前使用者擔任此角色 |
| 管理者 | 帳號、主檔匯入設定、備份還原及系統設定；不因系統管理權限自動取得業務核定權限 |

同一人可兼登記及複核角色；是否強制雙人確認待業務決定，P0不強制。所有操作記錄帳號，正式環境禁止用自行輸入姓名當作唯一身分驗證。權限須由桌面程式的業務與發布模組檢查，不能僅隱藏按鈕。以作業系統帳號識別使用者，並配合共用槽存取權限；查詢者不得具發布目錄寫入權。可直接寫入共用槽的使用者仍可能繞過程式，因此本架構的應用層角色與稽核不是防竄改安全邊界；若需強制隔離不同編輯角色，須另採受控服務或更細的檔案權限設計。

## 6. 資料結構

### 6.1 共通約定

- 主鍵採UUID；業務顯示編號另建，不用分組代碼作永久主鍵。
- 藥品／分組／ATC／廠商代碼皆文字型別，保留前導零。
- 金額使用十進位Decimal；禁止二進位浮點直接存價格。
- 日期採DATE、介面可顯示民國年；時間採UTC儲存、Asia/Taipei顯示。
- 有效期間採起日含、迄日不含；空白迄日代表無已知終止日，不代表永久有效。
- 歷史未知日期可為空，但須標記待確認；不得用會議日補成生效日。
- 儲存或發布前檢查資料版本，避免舊資料覆蓋新版。已確認資料可修正，但應建立新版本，保留原內容、修改人、時間與原因。
- 記錄建立者、建立時間、更新者、更新時間；正式資料以撤銷／取代保留，不硬刪。

### 6.2 核心資料表

| 表 | 必要欄位與用途 |
|---|---|

| case_drug | case_id、drug_code、品項在案件中的角色；一案多藥。 |

| recognition_revision | recognition_id、revision_no、類別、原始名稱、適用範圍原文、rule_json、附帶條件、effective_from／to、decision_id、case_id、確認狀態、supersedes_id、更正原因。 |
| meeting | id、會議類型（專家／藥事小組／共同擬訂／其他）、正式名稱、日期、次別、紀錄文件；同次會議可連多案。 |

| decision_drug | decision_id、case_drug_id、結果、條件及說明；同議案多品項可不同結果，未列入本次討論者不推定同意或不同意。 |

| master_drug | import_id＋drug_code唯一；品名、廠商、分組、ATC、劑型、成分／含量、單複方、規格數值／單位、支付價、原始註記及其他映射欄位。 |
| scope_snapshot | id、revision_id、import_id、規則雜湊、評估時間、符合／待確認數、confirmed_by／at。 |
| scope_member | snapshot_id＋drug_code唯一；符合條件路徑、人工確認結果／理由、當次分組及來源列定位。 |
| group_treatment | group_code、revision_id、適用調價方式（DET／第25條／待確認）、起訖日、依據、確認狀態。範圍部分涵蓋分組時不得自動推導整組。 |
| contract | id、合約編號、簽約廠商、簽訂／生效／到期日、文件版本、供貨義務摘要、狀態、原合約id。 |

| annotation_event | id、drug_code、revision_id、price_action_id、註記類別、動作（新增／改類／取消／更正）、生效日、依據、原事件id、確認狀態。 |
| attachment | id、原檔名、儲存鍵、SHA-256、大小、MIME、版本、上傳者／時間；另以關聯表連結案件、決議及合約。 |
| audit_event | 操作者、時間、實體與id、動作、前後差異、理由、請求id；只追加，不提供一般使用者修改。 |

補充：snapshot是當時判斷的證據，不會因新主檔而重算覆寫。未來新符合品項經確認後形成新快照／適用紀錄，不回溯偽裝成舊名單成員。

### 6.3 狀態欄位

- 案件處理狀態：辦理中、待補件、待提會、待後續辦理、已結案、撤回；與審議結果分開。
- 會議／品項結果：同意、不同意、附條件同意、補充資料後再議、暫緩、其他、待確認；保留決議原文，其他結果須說明。
- 案件結果摘要：尚無結論、全部同意、部分同意、全部不同意、撤回、其他。須連結形成摘要的會議／決議，由承辦確認；不得僅以最後一次會議日期自動認定最終結果。
- 原文不明或歷史資料缺失時使用待確認；不同意不等同取消既有資格。

- 登記確認：草稿、待確認、已確認、撤銷。未到生效日的已確認紀錄顯示「待生效」；現行有效由查詢日期計算。
- 簽約要求：須簽約、當時無須簽約、待確認。
- 合約狀態：辦理中、完成簽署、終止；是否已到期依日期顯示，無到期日不得猜測。
- 價格辦理：未辦、辦理中、已核定、撤回／取消；生效與否由日期另算。
- 主檔註記比對：一致、應有未有、主檔有但無完整依據、類別不同、無法判定。

## 7. 主檔匯入

1. 支援.xlsx及UTF-8 CSV；使用者選工作表、標題列及欄位映射，不依固定欄序。
2. 匯入必要欄位為藥品代碼。各類規則用到的欄位須存在，缺少時停用該類規則並明示原因，不以空白當不符合。
3. 同一快照一個代碼一列。完全相同重複列可在確認後合併；內容矛盾列阻止啟用。若來源為多期價格長表，先要求指定基準日期及期間映射，不任取第一筆。
4. 代碼去除前後空白；保留原值與正規化值；不自動把O改0。數值型代碼可能遺失前導零時列為錯誤，不自行補碼。
5. 規格分成數值及單位；只做經確認的單位映射。mL與L等換算須有明確規則，未知單位待確認。
6. 試匯入顯示總筆數、重複、缺漏、未知值及差異，確認後原子性啟用；失敗不改目前主檔版本。
7. 新快照保留舊版。比較新增／消失品項、分組、ATC、劑型、規格、廠商、價格及註記異動。
8. 主檔消失品項不自動刪除認定或解讀成取消給付；以來源涵蓋範圍判讀。
9. 保存來源文件、SHA-256及基準日。畫面明示目前引用哪一版主檔。

## 8. 條件選取與判定引擎

### 8.1 UI支援

分組多選、ATC完整碼多選、ATC前綴、核價劑型多選、單複方、規格數值與單位、藥品代碼納入／排除。選項由主檔產生；同時顯示代碼與中文說明。組合支援全部符合（AND）、任一符合（OR）、排除（NOT），以可展開條件群組表示。

畫面提供常用範本：依分組、依ATC加劑型、依分組加規格、指定品項、進階條件。首次不要求使用者看到JSON。

### 8.2 儲存格式

儲存結構化AST，禁止把Excel文字當SQL或執行程式。欄位、運算子及型別皆採白名單。條件例（依附檔邏輯整理）：

```json
{
  "op": "or",
  "children": [
    {"op": "and", "children": [
      {"field": "atc_code", "op": "starts_with", "value": "J06B"},
      {"field": "atc_code", "op": "not_in", "values": ["J06BB16"]}
    ]},
    {"field": "atc_code", "op": "in", "values": ["L04AA03", "L04AA04"]}
  ]
}
```

判定結果採符合／不符合／待確認三值。欄位缺失、未知單位或人工條件未完成時為待確認；NOT待確認仍為待確認。AND有不符合即不符合，否則有待確認則待確認；OR有符合即符合，否則有待確認則待確認。

前綴比對以文字起始位置，不做模糊包含。清單排除、含量及規格比較均按型別處理。空規則禁止當作全選；必須顯示錯誤。

### 8.3 特殊情形

- Warfarin同廠牌其他規格屬跨列關係。P0保留條件原文及人工確認清單；未釐清「同廠牌」與資料欄位對應前不得以相同藥商替代。
- 附檔條件末尾「=0」語意不清，不自動解讀。需業務確認後才編碼。
- 附檔RO5DA04疑似O／0問題，標示待確認，不靜默修正。
- ATC或規格條件可能只選到分組內部分品項。系統顯示「部分涵蓋分組」，分組調價方式須另確認，不能直接將該組全部排除DET。
- 多項認定同時涵蓋一藥或一分組：列出全部來源；若類別或有效期間衝突，阻止產生單一正式結果，待指定處理依據，不採最後儲存者優先。

## 9. 收案、會議及公告複核登記流程

### 9.1 基本收案與歷次會議（P0）

1. 取得編輯權後建立案件，登錄收文日／文號、廠商、申請事項、品項及承辦；歷史未知值標示待確認。
2. 新增或選取既有會議，建立議案與案件關聯，保存提案資料。
3. 會後逐次記錄專家建議或會議決議、條件及附件；同案重提新增議案紀錄，不覆蓋前次。
4. 同次議案不同品項分別登錄結果；不強制專家會議及共同擬訂會議固定各一次，也不虛構缺漏階段。
5. 同意或附條件同意者，依實際程序接續認定、簽約或價格辦理；附條件同意不直接當作已生效。
6. 不同意、撤回或暫緩者仍保存案件及全部會議資料。結案時記錄原因與依據；再提或重新開案須保留與前案關聯。
7. 案件結果不自動更動主檔註記；既有認定之取消或改類必須另建有依據事件。

### 9.2 公告複核登記


1. 開啟或建立公告案件，登錄公文、承辦及來源資料。
2. 搜尋既有認定項目；新增或建立變更版本，避免重複認定。
3. 登錄會議決議及範圍原文，選取主檔版本。
4. 點選條件，執行預覽；列出符合分組、符合藥品及待確認項目。
5. 核對認定範圍；涉及部分分組、排除或跨品項條件時明列提示。
6. 從範圍名單勾選本次調高品項，逐項登錄價格、簽約要求、合約及預定註記；範圍外品項不可直接勾入，須另補認定依據。
7. 儲存草稿／待確認。陳核階段不更新正式現況。
8. 核定後補正式文號、日期及各生效日期，複核登記者確認發布。
9. 在本機工作資料庫以單一交易保存版本、快照、品項事件及稽核紀錄，再依4.3完成共用槽版本發布。資料庫交易不代表跨檔案發布已完成；任何驗證失敗均不得切換共用版本。
10. 到生效日後，查詢結果依有效期間呈現；不以排程有無執行決定資料是否有效。
11. 匯入正式主檔後比對註記及價格，產生待核對清單；本系統不直接更新正式主檔。

現行案件須簽約卻缺完成簽署合約，不得確認調高結果。歷史案選「當時無須簽約」須有說明／依據；資料缺漏案可保留歷史紀錄，但顯示不完整，不能冒充已核驗。

## 12. Excel移轉與歷史案件建置

P0交付時由Claude實作匯入工具，依提供的Excel建立可核對的歷史資料。原Excel有提供的已通過、取消、改類及其他紀錄均保留；未提供的未通過案件不能編造，透過後續補登或新增來源匯入。

每筆暫存須具來源檔案雜湊、工作表、列號、原始欄位、解析結果及待確認問題。預覽並由使用者確認後才寫入案件／認定紀錄；缺生效日、決議或合約者可保留歷史資料但標記不完整，不自動視為已核驗現行有效。

可辨識的多次會議拆成獨立議案候選，保留原文供核對；不得把所有文字合併成最後一次結果。先建立案件及會議，再於有依據時連結認定。重複匯入同來源與列不得重複建案；跨來源相似案件僅列合併候選，不自行合併。


保留原檔與每列來源位置，再進入移轉暫存區，不直接寫成現行有效資料。

| 原欄位 | 移轉方式 |
|---|---|
| 調整時公告序號 | 原始參照；可能重複，不當主鍵 |
| 取消註記 | 取消候選事件；補依據與日期，不僅轉成目前否 |
| 分組代碼／名稱、成分／含量、劑型 | 與主檔核對；保存原文，矛盾待確認 |
| 分組項目 | 保存原值；意義未確認，不當自動計算筆數 |
| 討論歷程、價格異動歷程 | 原文保存，人工拆成多次決議／價格事件 |
| 類別 | 保留歷史名稱，另映射標準類別；含取消／歸零／未簽約混合文字須人工拆解 |
| 附帶決議 | 附帶條件及待辦；不自動解讀成取消命令 |
| 調整時公告名稱 | 認定名稱候選 |
| 篩選原則 | 規則草稿，解析後須預覽確認 |
| 原特殊品項_10512擬訂會議檢討結果、原篩選條件 | 保存歷史證據，不能覆蓋現行規則 |

| 有簽訂協議為不可替代必要/特殊(藥品代碼) | 合約／品項關聯線索；不能僅憑代碼清單視為已核驗正式合約 |

同一公告名稱、同一決議或同一分組重複列不自動合併。先顯示合併候選，使用者確認認定範圍是否相同。Rufinamide「參考特殊藥品精神調高、非認列」應保留價格案件及原文，不自動建立有效特殊身分。

## 13. 資料安全、備份與交接

- 正式資料、合約僅在獲准環境保存；桌面元件與字型隨程式離線供應，不依賴外部CDN。
- 附件採儲存鍵及雜湊，不以使用者檔名當任意路徑；防止路徑穿越。新版本不覆蓋舊檔。
- 上傳檔案型別及大小可設定；P0預設上限50MB。附件讀寫由程式角色與共用槽權限共同控管；檔案路徑不當作授權憑證。
- 備份選定已發布版本、其manifest及所有引用附件，完成雜湊驗證；不可複製寫入中的工作資料庫當作可靠備份。還原須取得編輯權，以新發布版本引用舊內容，保留還原原因及既有歷程，不直接改寫歷史release。
- 每次發布保留完整版本，大量匯入前另建備份；無持續執行主機時，不承諾關閉程式後仍每日自動備份。可由機關既有排程另辦每日備份；保存日數、RPO／RTO由單位確認。復原演練必須能還原認定、快照、合約附件及歷程關聯。
- 共用槽中斷時，附件作業顯示失敗，不回報上傳成功；確認依賴的附件不存在時阻止發布。
- 匯出包含匯出時間、查詢條件、主檔版本及基準日，避免又形成無法辨識版本的Excel。
- CSV／Excel匯出防公式注入；文字欄位不被當公式執行。
